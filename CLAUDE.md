# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Static marketing site + blog for **BonHeart Home Care** (Winnipeg, MB), recently rebranded from "TrueHeart". No build step, no package manager, no dependencies — plain HTML/CSS/JS. Deployed as static assets via Cloudflare Workers (see `wrangler.jsonc`, `assets.directory: "."`).

## Commands

- **Local dev**: no build step. Open any `.html` file directly, or serve the directory:
  ```
  python3 -m http.server 8000
  ```
- **Deploy**: Cloudflare Workers static assets (`wrangler.jsonc`, worker name `bonhearts`). Deploy with `wrangler deploy` if the user asks — do not deploy proactively.
- There is no test suite, linter, or build/bundle step in this repo.

## Structure

- `index.html` — the entire landing page (hero, founders, pricing, guarantee, FAQ, blog index, and the lead-qualification form) in one file, including all CSS in a `<style>` block and all JS in `<script>` tags at the bottom.
- 10 standalone blog article pages (`*.html` at repo root, e.g. `aging-in-place-home-safety-seniors.html`), each linked from `index.html`'s blog section.
- 8 service detail pages, one per service in the nav's "Services" dropdown, all built from one shared template (see **Service page template** below): `personal-care-services.html`, `post-hospital-convalescent-care.html`, `overnight-respite-care.html`, `senior-care.html`, `companionship-outings.html`, `household-support.html`, `specialized-care.html`, `disability-support-services.html`.
- `CNAME` — custom domain for GitHub Pages (`bonhearts.ca`).
- `sitemap.xml`, `robots.txt` — **still reference the old `trueheartshomecare.ca` domain**; check before trusting them as current, and flag/update alongside any other rebrand cleanup.

## Architecture notes

- **Every HTML file is fully self-contained.** There is no shared CSS/JS file, no templating, no includes. Each page (`index.html` and every blog article) duplicates its own `<style>` block with the same CSS custom properties (`--ink`, `--paper`, `--heart`, `--sage`, etc. — the brand palette) and its own copy of shared behaviors (nav scroll shadow, `IntersectionObserver`-based scroll-reveal, footer markup). **When changing shared visual/behavioral elements (nav, footer, logo, color tokens, reveal animation), the edit must be repeated across all 11 HTML files by hand** — there's no single source of truth to edit once.
- Blog articles share a common internal layout: a `.page-head`, `.toc` (table of contents), `<article>` body with `h2`/`h3`/callouts/`.cta-box`/`.suggest`/tables, all wired to the same scroll-reveal `IntersectionObserver` pattern at the bottom of the file.
- **Lead form** (`get-in-touch.html`, `#get-started` — moved here from the homepage at some point; despite the name, `index.html` no longer contains a form): a 6-step client-side JS wizard (no framework), restructured 2026-09-21 from an earlier 7-step version. Key pieces, all in the second `<script>` block near the bottom of the file:
  - **Step order**: 1 postal code &rarr; 2 contact details (name/email required, phone optional) &rarr; 3 who needs care (`relationship`, checkboxes/multi-select) &rarr; 4 decision-maker (radio) &rarr; 5 type of care (`care`, checkboxes/multi-select, options match the 8 service page names + "Not sure yet") &rarr; 6 timing (radio, final step). There is no funding question and no free-text "what's going on" textarea anymore — both were removed along with the `funding`/`hours`/`situation` fields entirely.
  - `steps` is read live from `.fstep` elements (`[...form.querySelectorAll('.fstep')]`), so **the step count, the progress bar, and the "Step X of Y" label are all derived from however many `.fstep` divs exist** — never hard-coded. Adding/removing a step just means adding/removing a `.fstep` block (with a correctly-numbered `id="err-N"`) and adding the matching `if (i === N)` branch in `validate(i)`, which is still index-based and needs to stay in sync with DOM order by hand.
  - `.opt input` can be a radio (single-select, clears sibling `.selected`) or a checkbox (multi-select, toggles its own `.selected` independently) — the change handler branches on `inp.type`. `val(name)` returns one value (radios/text inputs); `valAll(name)` returns an array of all `:checked` values (checkboxes) — used for `relationship`/`care`.
  - A `#btn-back` button (hidden via `.hidden` on step 1, shown otherwise by `show(i)`) just decrements `cur` — since steps are never removed from the DOM, going back and forward preserves whatever was already entered/checked, with no extra state-tracking needed.
  - `FORM_ENDPOINT` — a Make.com webhook URL; the form POSTs the final JSON payload here. Swap this constant to repoint the form at a different backend. **The Make.com scenario itself is not in this repo** — it can't be inspected or edited from here, only the payload this page sends to it.
  - `IN_AREA_FSA_PREFIXES` / `IN_AREA_FSA_EXACT` — Winnipeg-area Canadian postal FSA allow-list used by `inServiceArea()` to gate the "in area" flag.
  - `scoreLead(d)` — classifies each submission into `hot` / `warm` / `nurture` / `out-of-area` based on `in_area` and `timing` only (the old `funding`-based `budget-mismatch` branch and its `success-budget` screen were both removed 2026-09-21).
  - Payload fields as of 2026-09-21: `postal, name, email, phone, relationship, relationship_text, decision, care, care_text, timing, submitted_at, source, in_area, lead_score`. `relationship` and `care` are arrays; `relationship_text`/`care_text` are the same values joined with `", "`, sent alongside the arrays specifically so Make.com's existing text-based mappings (email templates, sheet columns) keep working without needing to parse an array.
  - On submit, routing goes to one of three `#success-*` screens keyed by `lead_score` (`success-qualified`, `success-out-of-area`, `success-nurture`). No redirect — it's an inline DOM swap (`form.style.display='none'` + show the matching screen) on the same page.
  - **Booking step (added 2026-09-21)**: `#success-qualified` has two inner states — `#qualified-booking` (shown first, holds a Cal.com inline embed at `#my-cal-inline-30min`) and `#qualified-confirmed` (hidden until booking completes). `showQualifiedBooking(data)` is called only when a lead actually routes to `success-qualified` (hot/warm) — this is also the only point that lazily injects Cal's loader script and `canvas-confetti` (from `cdn.jsdelivr.net`, pinned version); neither loads on page load or for the other two outcomes.
    - `CAL_NAMESPACE`/`CAL_LINK`/`CAL_ORIGIN` constants near the top of the script — `CAL_LINK` is `"david-bolarinwa-zgwdul/30min"` (set 2026-09-21).
    - The embed is prefilled from the form's own data: `name`, `email`, and a `notes` string combining `care_text` + the postal code (Cal's inline `config` object supports a `notes` key directly, confirmed against Cal's own docs — no separate API call needed).
    - `cssVarsPerTheme.light['cal-brand']` is read live from the page's own `--heart` custom property via `getComputedStyle`, not hardcoded, so it can't drift from the site's actual accent color.
    - The booking event listened for is `bookingSuccessfulV2` (`Cal.ns['30min']('on', {action:'bookingSuccessfulV2', callback})`) — this is Cal's current event; the older `bookingSuccessful` is deprecated. On that callback: clear `#my-cal-inline-30min`'s content (`innerHTML=''`), swap `#qualified-booking`/`#qualified-confirmed` visibility, fire the `canvas-confetti` burst (skipped under `prefers-reduced-motion: reduce`), then call `guardAgainstPostBookingRedirect()`.
    - **`guardAgainstPostBookingRedirect()` — this exists because of a real, reproduced bug (2026-09-21/22).** Cal's own SDK (`embed.js`) runs in *our* page with full privileges, since we're the ones who load it — it isn't confined to the iframe. Even after tearing the iframe out (which fixed one redirect), a *second* redirect to the homepage kept happening, ~5s after our own confirmation screen was already showing. That timing (a delay, not instant) means it's almost certainly `embed-core.js` itself scheduling a `setTimeout`-based redirect on our page's own `window`, likely driven by a "Redirect on Booking" setting on the Cal.com event type (Cal.com dashboard → event type → Advanced tab — outside this repo, unverified as of this note; worth checking/disabling there too). Since Cal's internal message handler runs before it invokes our `on()` callback, we can't stop the timer from being *scheduled* — but we don't need to: `clearTimeout`/`clearInterval` can cancel *any* pending timer at any point before it fires, regardless of who created it, and browser timer IDs are small sequential integers, so sweeping every ID up to the current highest one cancels it without knowing which ID it is. The guard runs this sweep on every `requestAnimationFrame` (not `setTimeout`/`setInterval`, so it can't cancel itself) for 8 seconds — comfortably past the observed ~5s — and also watches for and removes any injected `<meta http-equiv="refresh">` tag, the other common self-redirect mechanism. `fireConfetti()` is called *before* starting this sweep specifically so it can't clear any startup timer confetti's own animation might use.
    - `#cal-embed-wrap` is `width:100%` with a `min-height` only (no fixed height, no `overflow:scroll`) so Cal's own auto-resize can take over, per Cal's guidance for inline embeds.
- SEO metadata (title, description, canonical, OpenGraph, Twitter card, and a JSON-LD `HomeHealthCareService`/article schema block) is hand-duplicated in the `<head>` of every page — update all relevant occurrences together when changing site-wide facts (phone number, address, business name). Service pages do **not** carry the JSON-LD block (only `index.html` and blog articles do).

Identical on all 8 pages and must stay byte-identical to `index.html`'s version if either is ever edited — check both when changing this copy. Sits before the explore-services carousel (moved there 2026-09-15, at the user's request — was after it before that).
  5. **`.service-carousel` / `.service-grid`** ("Explore our other home care services") — cross-links to the other 7 service pages using the same photo `.service-card` markup/CSS as `index.html`'s `#services` grid (circular photo frame, `h3`, `p`, `.read` "Learn more →"), in homepage order, self excluded, on a `.wrap.wide` (`max-width:1080px`, vs. the page's base 720px `.wrap`) so cards match the homepage's per-card width — don't reuse `.wrap.wide` narrower than this without re-checking card text doesn't clip. This is now the last section before the footer.
     - **Carousel mechanics**: single-row `display:flex` scroller (`overflow-x:auto`, `scroll-snap-type:x mandatory`, native scrollbar hidden). `.service-card` flex-basis `82%`/`44%`/`22%` at base/`641px`/`901px` (the page's existing breakpoints) so a sliver of the next card always peeks. `padding:20px 20px 40px` keeps the first/last card and the hover-lift shadow off the scroll container's edges.
     - **Arrows**: real `<button>`s, `.carousel-arrow-prev`/`-next` (`aria-label="Previous/Next services"`), circular, `var(--heart)`/`var(--heart-deep)`/`var(--shadow)`/`var(--shadow-lift)` tokens. Disabled natively at each end (`disabled` attribute, faded via `:disabled{opacity:.35}`). Keyboard focus uses the page's existing global `button:focus-visible` — no separate rule.
     - **Edge fades**: `.carousel-fade-left`/`-right`, gradient from `var(--paper-dim)` to `transparent`, `pointer-events:none`, hidden via `.service-carousel.is-start`/`.is-end`.
     - **JS** (inline `<script>` near the bottom, byte-identical on all 8 pages): one IIFE queries `.service-carousel`, computes a one-card scroll distance from the first `.service-card`'s live width + the flex `gap`, and calls `track.scrollBy({left, behavior})` on arrow click — `behavior` is `'auto'` under `prefers-reduced-motion: reduce` (checked directly in JS, since an explicit `behavior` overrides CSS `scroll-behavior`). A `scroll`/`resize`-driven `update()` toggles `disabled` and `is-start`/`is-end`. No touch listeners — native swipe/trackpad scrolling and snap are untouched.
